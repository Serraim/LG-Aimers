## 1. 먼저 나오는 질문

> "LightGBM 을 쓰면 어떤 컬럼이 중요한지 자동으로 정해지는 것 아닌가?
>  그런데 피처를 바꾼다는 것이 무슨 뜻인가?"

**절반만 맞다.**

LightGBM 이 자동으로 하는 일은 **"주어진 컬럼 중에서 어느 것을 어느 값에서 자를지"** 를 고르는 것이다.
주어지지 않은 컬럼은 만들어내지 못한다.

### 나무 모델이 하는 일

나무는 **한 번에 한 컬럼만** 보고 자른다.

```
        strikes_before <= 1 ?
          /            \
        예              아니오
      inning<=5?      balls_before<=2?
```

이 구조로는 **두 컬럼을 조합한 값**을 직접 표현할 수 없다.
`strikes_before - balls_before` 를 쓰고 싶으면 다음처럼 여러 단을 쌓아 근사해야 한다.

```
strikes<=0 & balls<=0        ->  차이 0
strikes<=0 & balls<=1        ->  차이 -1
strikes<=1 & balls<=0        ->  차이 +1
...                              (12개 조합을 전부 따로 학습)
```

즉 **표현은 가능하지만 비싸다.** 트리 깊이와 데이터를 그만큼 더 쓴다.
그 값을 컬럼으로 미리 만들어 주면 **한 번의 분기로 끝난다.**

### 나무 모델이 절대 못 하는 일

더 중요한 것은 이쪽이다.

```
asof_pitcher_success_rate = 0.52   (2019년 투수)
asof_pitcher_success_rate = 0.52   (2024년 투수)
```

두 값은 컬럼 상으로 **똑같다.** 그런데 의미는 다르다.
2019년 리그 평균은 0.5647, 2024년은 0.4861이기 때문이다.

```
2019년의 0.52  ->  리그 평균보다 낮음  (평균 이하 투수)
2024년의 0.52  ->  리그 평균보다 높음  (평균 이상 투수)
```

나무는 `season` 컬럼과 `asof_pitcher_success_rate` 컬럼을 **각각** 자를 수는 있어도,
`success_rate - league_avg[season]` 이라는 **뺄셈 결과**를 만들어낼 수 없다.
나무는 사칙연산을 하지 못하고 **경계로 자르기만** 한다.

그래서 이 값은 사람이 계산해서 컬럼으로 넣어줘야 한다. 그것이 `rate_plus` 다.

### 실제로 그랬는가

우리가 만든 15개 중 `pitcher_rate_shrunk` 하나가 **전체 중요도의 23.39% 로 1위**다.
원본 47개 중 어떤 컬럼보다도 많이 쓰였다.

```
1위  pitcher_rate_shrunk   23.39%   <- 우리가 만든 것
2위  season                12.19%
3위  game_type              9.37%
4위  asof_pitcher_success_rate  4.18%
```

15개 전체가 중요도의 **34.7%** 를 차지한다.
피처를 만드는 작업이 무의미하지 않았다는 실측 근거다.

### 요약

```
LightGBM 이 하는 것    주어진 컬럼 중 무엇을 어디서 자를지 고른다
사람이 해야 하는 것    자를 수 있는 컬럼 자체를 늘린다
```

## 2. 컬럼 49개의 실제 행방

```
train.csv   49개
test.csv    48개
모델 입력   62개
```

### 49 -> 48 : 정답 컬럼이 빠진다

| 컬럼 | 이유 |
|---|---|
| `control_success` | 맞혀야 하는 정답. test 에 없다 |

### 48 -> 47 : 식별자가 빠진다

| 컬럼 | 이유 |
|---|---|
| `row_id` | 몇 번째 줄인지를 나타내는 번호. 내용이 없다 |

`row_id` 를 넣으면 안 되는 이유는 단순히 무의미해서가 아니다.
행 번호는 데이터가 정렬된 순서를 담고 있어서, 모델이
"앞쪽 번호는 성공률이 높다" 같은 **평가 데이터에서 재현되지 않는 규칙**을 학습할 수 있다.

### 47개는 전부 사용한다

**하나도 버리지 않았다.** LightGBM 은 쓸모없는 컬럼을 알아서 거의 안 쓰기 때문에,
사람이 미리 지우는 것보다 넣어두는 편이 안전하다.

실제로 거의 안 쓰인 컬럼들이다.

```
runner_on_1b     0.019%
runner_on_2b     0.022%
runner_on_3b     0.028%
top_bottom       0.055%
base_state       0.082%
```

주자 위치는 제구 성공 여부와 거의 관계가 없다는 뜻이다.
**이것이 "LightGBM 이 알아서 정한다" 는 말이 맞는 부분이다.**

### 47 -> 62 : 우리가 15개를 더했다

여기가 "피처를 바꿨다" 는 부분이다.
**원본을 고치거나 지운 것이 아니라 15개를 추가한 것이다.**

## 3. 우리가 만든 15개

전부 `scripts/script.py` 의 `add_domain_features()` 안에 있다.
학습(`build_feat_model.py`)과 추론(`script.py`)이 **같은 함수**를 호출하므로 어긋날 수 없다.

### 리그 평균 대비 (야구의 ERA+ 개념)

| 피처 | 계산 | 왜 |
|---|---|---|
| `rate_plus` | 투수 성공률 - 그 해 리그 평균 | 시대 보정. 나무가 못 하는 뺄셈 |
| `batter_rate_plus` | 타자 성공률 - 그 해 리그 평균 | 위와 동일 |

리그 평균은 **train 에서만** 계산해 표로 저장한다.

```
2019  0.5647      2023  0.5000
2020  0.5327      2024  0.4861
2021  0.5328      2025  0.4747   <- 학습 시즌 추세로 외삽
2022  0.5289
```

### 표본 크기 보정 (평균으로의 회귀)

| 피처 | 계산 |
|---|---|
| `pitcher_rate_shrunk` | `(n × 성공률 + k × 리그평균) / (n + k)`, k=500 |

**중요도 1위(23.39%) 피처다.**

투구 10개만 던진 투수의 성공률 0.80과, 5000개 던진 투수의 성공률 0.55 중
믿을 만한 것은 후자다. 표본이 적을수록 리그 평균 쪽으로 끌어당긴다.

```
n=10    ->  거의 리그 평균값
n=5000  ->  거의 본인 성적 그대로
```

원본 컬럼에는 성공률(`asof_pitcher_success_rate`)과 표본수(`asof_pitcher_n`)가
따로 있을 뿐, **둘을 결합한 값은 없었다.**

### 볼카운트

| 피처 | 계산 | 야구 상식 |
|---|---|---|
| `count_state` | `balls×3 + strikes` | 12가지 볼카운트를 하나의 상태로 |
| `count_edge` | `strikes - balls` | 투수가 유리한가 불리한가 |
| `is_pressure` | `balls == 3` | 볼넷 직전. 반드시 넣어야 함 |
| `is_putaway` | `strikes == 2` | 삼진 직전. 유인구를 던짐 |

### 경기 진행

| 피처 | 계산 | 야구 상식 |
|---|---|---|
| `progress` | `(inning-1)×3 + outs` | 경기가 얼마나 진행됐나 |
| `tto` | `min(3, (inning-1)//3 + 1)` | 같은 타자를 몇 번째 상대하나 |

`tto` 는 세이버메트릭스의 **times through the order penalty** 개념이다.
같은 타자를 두 번째, 세 번째 만날수록 투수가 불리해진다는 통계.

### 좌우 매치업

| 피처 | 계산 |
|---|---|
| `hand_matchup` | `pitcher_hand×2 + batter_hand` (4가지 조합) |
| `same_hand` | 좌우가 같은가 |

### 컨디션

| 피처 | 계산 |
|---|---|
| `form_gap` | 최근 5경기 성공률 - 통산 성공률 |
| `form_gap_mid` | 최근 5경기 한복판률 - 통산 한복판률 |

양수면 요즘 폼이 좋다는 뜻. **뺄셈이라 나무가 못 만든다.**

### 상대 우열

| 피처 | 계산 |
|---|---|
| `skill_gap` | 투수 성공률 - 타자 성공률 |
| `exp_gap` | `log1p(투수 표본) - log1p(타자 표본)` |

| 3 | `game_type` | 9.37% | 원본 |
| 4 | `asof_pitcher_success_rate` | 4.18% | 원본 |
| 5 | `asof_pitcher_reverse_rate` | 3.68% | 원본 |
| 6 | `asof_batter_success_rate` | 3.51% | 원본 |
| 13 | `form_gap` | 1.74% | **신규** |

```
신규 15개 합계 비중   34.7%
신규 최고 순위        1위
```

### 실패한 신규 피처

만든 것이 전부 쓸모 있었던 것은 아니다.

```
tto           0.005%   <- 62개 중 꼴찌
is_pressure   0.029%
is_putaway    0.094%
```

`tto` 는 야구 이론상 근거가 확실한데도 거의 안 쓰였다.
`inning` 컬럼이 이미 있어서 **정보가 중복**됐기 때문으로 보인다.
볼카운트 관련 이진 피처들도 `count_state` 가 같은 정보를 더 잘 담고 있어 밀렸다.

**이론이 맞아도 데이터에 이미 있으면 중요도가 오르지 않는다.**
다음에 피처를 만들 때 기억할 점이다.

## 5. 규칙 준수 근거

AGENTS.md §2 는 **평가 데이터의 각 행을 독립적으로 예측**할 것을 요구한다.

### 15개 중 14개

전부 **같은 행 안의 값끼리만** 계산한다. 다른 행을 보지 않는다.

```python
X["count_edge"] = X["strikes_before"] - X["balls_before"]   # 같은 행
X["form_gap"]   = X["...prev5..."] - X["...success_rate"]   # 같은 행
```

### 나머지 1개 (`league_avg` 조회)

`rate_plus`, `batter_rate_plus`, `pitcher_rate_shrunk` 는 리그 평균 표를 참조한다.
이 표는 **train 으로만** 만들어 artifact 에 박아둔 고정 숫자 8개다.
추론 때는 `season` 값으로 **조회만** 한다.

```python
la = X["season"].map(league_avg)      # 고정 표에서 꺼내기
```

test 를 보고 계산하지 않으므로 행 독립성이 유지된다.

### 실측 검증

`scripts/check_rules.py` 및 245,789행 규모 재현 시험 결과.

```

전체 순서를 거꾸로 뒤집기                  최대차 0.000e+00
1,000행만 잘라서 넣기                      최대차 0.000e+00
추론 4.6초 / 0.84 GB                       (제한 600초 / 28 GB)
```
